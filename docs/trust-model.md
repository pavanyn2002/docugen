# The trust model

This is the part worth understanding. Everything else is mechanics.

## Why it exists

The failure this tool is built around is specific. A developer is asked how something works, asks a model, gets a plausible answer, pastes it to QA. QA files it as the specification. Nobody marked it as a guess, so six months later it is indistinguishable from something that was checked — and when the software behaves differently, nobody can tell whether that is a bug or the note was wrong.

Generated documentation makes this worse at scale, not better, unless the generated text carries its own provenance. So every line docgen writes belongs to exactly one lane, and the lane is visible on the line itself — never inferred from which page it is on or how confident it sounds.

## The three lanes

### `verified`

Came from a parser reading real code, or from a named developer's recorded answer.

Rendered without a badge on the structural pages (`routes.md`, `api.md`, `schema.md`, …) because those pages are entirely verified and say so at the top. Rendered with an explicit `verified` badge on behaviour pages, where it sits next to inferred content.

**What it guarantees:** every statement traces to a file and line, or to a person and a date. If a `verified` statement is wrong, either the code changed and the docs are stale (`docgen check` catches that), or a developer answered incorrectly (`docgen answer` again, and it is replaced).

### `inferred`

A model read the code and wrote this. Every claim carries links to the lines it cites.

**What it guarantees:** the claim is *cited*, not that it is *correct*. The schema rejects any claim with no evidence, so you can always check it — but nobody has. Treat it as a starting point for a conversation, not as a specification.

### `unknown`

The model could not determine this from the code, so it recorded a question instead of guessing.

**What it guarantees:** nothing was invented. The gap is visible and named, with an explanation of why it could not be established, and usually a short list of likely answers.

## How the lanes are kept apart

Four mechanisms, none of them prompting:

**1. An enforced import boundary.** `src/extract/`, `src/surface/`, `src/render/`, `src/config/`, `src/util/` and `src/types/` are the static lane. They may never import from `src/infer/`, `src/questions/`, or `src/agents/`. This is checked by a test that scans the source tree, including dynamic imports. Output from the static lane is stamped `verified`; if an extractor could call a model, that stamp would be a lie.

**2. Schema validation of model output.** The model must return JSON matching a strict schema. A claim with no `evidence` array is rejected. Unknown keys are rejected. Output that does not validate is discarded — never salvaged into prose — and the surface is reported as one docgen could not describe.

**3. Answers as an overlay, not an edit.** A developer's answer is stored separately in `docs/.answers/` and injected into every future prompt. The model is told what has already been confirmed, so it cannot contradict it, and the answered question is never asked again. Answers survive regeneration, refactors, and prompt-version changes.

**4. Separation on the page.** `README.md` links behaviour documentation from its own section, deliberately outside the contents table — because that table is followed by the sentence "no part of it was generated by a language model", and that sentence has to stay true.

## What each artefact is

| File | Lane | Written by |
|---|---|---|
| `routes.md`, `api.md`, `schema.md`, `jobs.md`, `config.md` | `verified` | Parsers |
| `diagrams/*.mmd` | `verified` | Parsers |
| `behaviour/*.md` | mostly `inferred`, with `verified` answers inline | A model, plus developers |
| `requirements.md` | `verified` | Developers, via `answer` + `triage` |
| `test-cases.md`, `traceability.md` | `verified` | Derived from requirements |
| `docs/.cards/` | `inferred` | A model. Regenerated; do not hand-edit. |
| `docs/.answers/` | `verified` | Developers. Never regenerated. |
| `docs/.requirements/` | `verified` | Developers. Never regenerated. |

## The one page that is a specification

`requirements.md`. Every entry was answered by a named developer and then classified by one. Nothing in it came from a model.

It also states its own coverage: if answers are still untriaged, the page says how many and warns that whatever they establish is missing. A specification that quietly omits things is how the original problem comes back.

## Rules the tool will not break

- Never state a behavioural claim without a badge.
- Never fill a gap with a plausible value. A gap is recorded; an unknown becomes a question.
- Never read or record `.env` **values** — only variable names and where they are used. `config.md` is committed, and those files hold credentials.
- Never treat an OpenAPI or Swagger annotation as truth. It is cross-checked against the code, and disagreements are reported both ways. Code is what runs; an annotation is a claim about the code that may have rotted.
- Fail loudly on malformed input, silently on absent input. A corrupt `docs/.answers/` file is an error, not a file to skip — skipping one would silently demote confirmed knowledge back to a guess.

## What this costs you

Precision, in exchange for a lot of "not determined". A page full of gaps looks worse than a page full of confident prose. It is worth it: a gap is a question someone can answer in ten seconds, and a wrong confident sentence is a bug report six months from now that nobody can resolve.

The gaps are also the roadmap. `docgen ask` turns them into a queue, and every answer permanently converts one into fact.
